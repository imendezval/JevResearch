# JevResearch — Phase 3: live Jev controller over valid experiments

## Mission and prerequisites

Start only after Phases 1 and 2 pass. Add `JevController` behind the existing controller boundary. On the **same** CIFAR-10 task, search space, candidate generator, training protocol, budget, and history format as `RandomController`, Jev makes one bounded typed `Choice` among valid candidate IDs. Code retains validation, objective comparison, budget control, and all side effects. Do not add TPE/CMA-ES, LLM escalation, code generation, new modalities, or a large prompt framework.

This establishes a working controller, **not** a claim of improved AutoML. Jev may be poorly suited to choosing numeric hyperparameters from brief tabular histories; even a valid API response is only a proposed experiment. TypeSafe documents `Choice` as selecting among supplied criteria and notes that Jev 1.13 struggles with numeric precision and irrelevant state. Recheck its official [Python SDK](https://docs.typesafe.ai/sdk/python), [Choice](https://docs.typesafe.ai/primitives/choice), [API response](https://docs.typesafe.ai/api), [models](https://docs.typesafe.ai/models), and [model limitations](https://docs.typesafe.ai/model-jaggedness/jev-1.13) at implementation time. The current documented request uses `state`, `model`, and `questions: {next_trial: Choice(instructions=..., criteria={candidate_id: description})}`; the response places the selected ID under `answers.next_trial.choice` with probabilities/confidence, model, and usage. Verify names against the installed SDK instead of assuming this snapshot stays current.

## Adapter and request

- The TypeSafe-specific code lives in one adapter/transport module. Prefer the official `typesafe-sdk` in an optional `jev` dependency with a reproducibly pinned version. If its retry/timeout behavior cannot be bounded as required below, use the documented HTTP API behind the same adapter. Do not add direct SDK imports to the core or CIFAR task.
- Expose an explicit model setting. For a comparison, pin an available **versioned** model ID, e.g. `jev-1.13.0` if still supported; record both requested and response model IDs plus SDK version. An alias such as `jev-latest` is acceptable for exploration only if the resolved response model is retained. Do not claim a model version that the response did not confirm.
- Save the exact ordered offer from Phase 1. Construct one `Choice` question with candidate IDs as option keys and concise, distinct descriptions: full resulting config, operator and changed fields relative to the parent. State contains task/protocol and objective direction, remaining trial slots, best completed result, up to five recent outcomes, and at most 6–8 eligible candidates. Produce numeric deltas/ranks in code; include no images, raw logs, absolute secret paths, credentials, or huge history. Bound serialized request size and log any deterministic truncation. The same offer generation and cap applies to random and Jev; candidate order is deterministic or reproducibly shuffled and saved for both.
- Validate answer type and selected ID against the **persisted** offer. Keep the returned distribution/confidence as audit observations, not as calibrated probabilities of validation improvement. Do not let Jev invent a configuration, change the objective, or return an unoffered trial. Missing/malformed output is an explicit controller failure.

## Calls, failures, and resume

- Before each API call, persist a logical decision-attempt record with the sanitized exact state/question/options, offer ID, requested model, and timestamp. After the call, record sanitized structured response or error, latency, response model, usage fields if supplied, selected ID, and validation outcome. Commit a valid selection plus its pending trial **transactionally** as in Phase 1. If the process crashes after selection but before trial launch, resume the same pending trial without another Jev call.
- Auth uses the official `TYPESAFE_API_KEY` environment mechanism or its documented equivalent. Never log, print, or commit a key, authorization header, whole process environment, or a `.env` file. Set explicit request timeout and bounded retries/backoff; avoid stacking unlimited application retries on SDK retries. Keep a small configurable cap on logical Jev calls/decision attempts for a run. A timeout may have reached the provider; mark its outcome unknown rather than pretending it incurred no call or cost.
- On 401, transport/rate-limit exhaustion, malformed output, or an invalid candidate ID, persist the failed decision and stop the Jev session in a clear resumable state. Resume reuses the **same outstanding offer and request state**, and may make a new logged API attempt; it consumes no experiment until a valid selection is committed. No silent random fallback. A training failure after a committed selection remains a failed **trial**, distinct from a controller failure. Preserve every attempt; do not overwrite a previous response on retry.
- An offline fake transport is solely a test double, injectable without network/key. Test success, bad IDs, malformed probabilities, timeout, and storage. It must never be labeled as a live Jev run in the CLI, history, or comparison output. A separate named scripted controller is optional for demonstrations.

## Comparison output

Export best validation accuracy versus **attempted trials** and elapsed wall time for random and Jev, including failed/interrupted trials and controller failures separately. Report logical API calls; report lower-level retry count only if observed, otherwise label it unavailable. Keep input/output token usage if supplied. Compute money from an explicitly recorded provider pricing snapshot only when trustworthy; otherwise show cost unavailable. Do not call wall time GPU-active time.

Document a paired comparison recipe: same CIFAR train/validation indices, architecture, operators/offer cap, training budget, hardware, source/protocol version, baseline config/seed, and search-seed/trial-seed schedule; only the controller varies. The changing candidate trajectories after the first choice are part of the comparison. Pin/log model and option order. Use several independent paired seeds before any superiority claim, report variability and all runs, and keep the test set untouched. A single two-trial run proves integration only. Do not tune Jev wording on the comparison runs and then present them as untouched evaluation; version the question/criteria and disclose changes.

## Verification and acceptance gate

Offline automated tests must cover exact request/option mapping, size/redaction, response validation, model/usage logging, failed call with zero attempted trials, retry of the saved offer, committed pending trial without a duplicate call, and ordinary training failure. Re-run the complete Phase 1/2 tests and smoke paths. A fake response does **not** validate the real provider integration.

When a key and network are available, make one real bounded Jev selection in a synthetic or tiny fixture session and inspect its saved request/response without secrets. Then run a real CIFAR-10 baseline and at least one **Jev-selected** candidate under the same fixed short protocol as Phase 2, if dataset/compute permit. Set explicit small trial, time, and API-call budgets. Report the actual response model, selection, latency, and usage. If key/network is unavailable, finish and commit offline implementation, document the exact live command, and mark the live gate **blocked/unverified**. If real CIFAR is unavailable, distinguish API verification from end-to-end CIFAR verification. Never claim Phase 3 fully passed without both live API selection and real CIFAR execution.

- Inspect the repository, Phase 2 history/schema, Git status, user edits, and current official docs first. Record the field mapping you used in adapter tests. Proceed autonomously on routine implementation choices and keep migrations compatible with existing history.
- Commit coherent passing units such as adapter/offline tests, decision ledger/resume, CLI/comparison/docs. Stage only owned files, inspect the staged diff, and keep keys, `.env`, run DBs, data, logs, and checkpoints out of commits. No manufactured history, amend/rebase/reset, push, or unrelated user edits. Report a missing author identity or other commit blocker without inventing one.
- Finish and commit executable changes before the live verification session; do not change code, criteria, dependencies, or model ID mid-session. If a live call reveals a bug, preserve the failed record, fix and commit, then begin a new session. Keep paid calls bounded and avoid an accidental multiseed sweep during validation.
- Review the diff for credential leakage, unbounded retries, invalid-ID acceptance, duplicate trial on resume, fake/live labeling, model-alias drift, biased candidate ordering, and unsupported benchmark claims. Report commits, exact tests and commands, the live/offline status of both gates, a redacted representative decision, and observed call usage. Stop at this phase boundary.
