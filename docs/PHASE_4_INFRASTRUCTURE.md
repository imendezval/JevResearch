# JevResearch — Phase 4: reliable studies and experiment infrastructure

## Starting point and mission

The [JevResearch repository](https://github.com/imendezval/JevResearch) already has immutable specs, seeded offers, a SQLite trial/decision ledger, subprocess training, interruption handling, JSON export, and a two-session random/Jev comparison. At inspection on 2026-09-24 (`main` at `623237e`), there was no versioned multi-run study configuration or scheduler, no explicit lock/orphan-worker recovery, and the exported elapsed wall time included pauses. The code records GPU-active time and money as unavailable. Reinspect the current branch before implementing; do not recreate features that have since landed.

**Outcome:** one versioned study specification can run and resume a small set of paired campaigns, then produce an honest, comparable report. A crash must not produce a duplicate trial or leave a training process able to race a resumed session. This phase strengthens the existing random/Jev system. Do not add another search algorithm, a new ML task, an LLM, or distributed execution.

Phase 1–3 tests are a prerequisite. The public checkout's 34 tests passed at inspection, with three tests skipped because optional Torch or TypeSafe SDK dependencies were absent. The repository alone does not demonstrate a live CIFAR/Jev acceptance run; inspect any local evidence and distinguish unverified gates in the final report. Infrastructure work can proceed offline, but do not claim a live research comparison without real data and API calls.

## Study specification and runner

- Add a strict, versioned JSON study specification, using Python 3.10-compatible parsing. Include task/protocol, shared dataset/split, training budget, attempted-trial budget, device and timeout, controller arms, ordered search seeds, candidate limit, and output root. A study has a content fingerprint from a canonical normalized specification and executable source digest. Validate all fields, reject unknown keys, and record resolved defaults and local path overrides. Do not put credentials or API keys in files or exported manifests.
- Support `study run`, `study resume`, and `study report` (or equally clear commands). Schedule at most one trial process at a time. A study registry maps `(study ID, arm ID, search seed)` to one existing session; rerunning the same command must resume/skip that session, never create a duplicate. The shared baseline and trial-seed schedule must match across paired arms. Keep `run`, `cifar-run`, `resume`, `cifar-resume`, `show`, `export`, and the existing `compare` working.
- Freeze protocol and executable source per campaign as before. A study resume checks the normalized specification, source digest, dataset/split, and controller/model settings before scheduling more work. Changes require a new study. Existing databases remain readable through an explicit migration. Mark an unavailable key, dataset, or device as a **blocked arm**, not as a fake success or an implicit fixture substitution. A study can report completed arms while others are blocked.
- Put a conservative total active-time cap and per-trial timeout in the spec. The active-time cap prevents launching another trial when exhausted; it does not silently shorten the fixed training budget of a trial already running. Record the stop reason. Keep the existing attempted-trial budget authoritative and one worker per study; no early stopping, pruning, or parallel GPU workers in this phase.

## Process safety and recovery

The current subprocess executor creates a separate process group, while the runner treats a trial left `running` as interrupted on resume. Address the case where the parent dies but the child survives, plus two CLI processes trying to resume the same local study. Implement a single-host ownership mechanism (for example an OS-held lock plus persisted worker identity and a parent-death/reaper strategy). It must cover the spawn-to-PID-record race. On recovery, either establish that the old worker is gone or stop with an actionable diagnostic; never kill a process based on a bare reused PID, mark a still-running worker interrupted, or start a duplicate trial. Do not require a network service for local SQLite.

Keep pending-trial and saved-offer semantics from Phase 1–3. A recovered completed worker result is accepted only if its recorded spec, trial identity, and artifact integrity match; otherwise record the interrupted attempt and preserve diagnostic artifacts. Do not turn a prior interrupted attempt into a retried training run. Add focused crash/dual-launch tests that actually exercise the ownership transition, rather than only mocking a status flag.

## Timing, artifacts, and accounting

- Separate **calendar elapsed** (includes pauses) from **observed active study time** (recorded training, controller calls, and orchestrator activity). Record per-trial process wall time, worker-reported training time, controller-call latency, and time with unknown outcome after a crash. Do not double-count nested durations. Persist completed intervals so resume does not reset the clock. If an unknown interval could exhaust the active-time cap, stop until it is reconciled. Report a missing measurement as unavailable. Use observed active time for efficiency curves; do not relabel calendar elapsed or CUDA allocation as GPU-active time.
- Keep `gpu_active_seconds` unavailable unless a validated device-attributable measurement is implemented. Optional pricing input may estimate compute occupancy cost from declared hourly rate times process wall time, explicitly labeled an **estimate**. Jev money may be calculated only from an archived pricing snapshot and observed complete token usage; otherwise retain unavailable. Distinguish logical API attempts from lower-level retries whose counts are unknown.
- Add an opt-in `none|best` model-checkpoint policy; default `none`. For `best`, save a completed trial's model `state_dict` and small provenance manifest atomically, with SHA-256, spec fingerprint, protocol/split identity, model version, and library versions. Retain the current best checkpoint, safely prune old intermediates, and mark intentionally pruned artifacts in history. After crash, reconcile temp files and ownership before cleanup. Verify loading and repeating validation on a fixture, with a documented tolerance where deterministic equality is not possible. No mid-epoch training resume or automatic official-test evaluation.
- Generalize report/export beyond the hard-coded random-versus-Jev pair. Validate equality of the fields that make arms comparable; give exact mismatch reasons and refuse a combined performance curve for incompatible arms. Include every attempted trial, failure, interruption, controller error, blocked arm, and seed. Export machine-readable per-seed trajectories plus a compact aggregate table/plot for best validation metric versus attempts and observed active time. Report median and individual seeds; do not draw uncertainty bands or superiority claims from a single seed. A lightweight optional plotting dependency is fine.

## Verification and bounded demonstrations

Tests: strict config parsing/fingerprint; idempotent study run/resume; changed config/source refusal; preserved Phase 1–3 history through migration; concurrent launch refusal; parent/child crash and orphan recovery; active-time accounting across a long pause; cost marked estimate/unavailable correctly; best-checkpoint creation/load/prune; report compatibility rejection and inclusion of failures. Keep tests CPU-sized and avoid paid calls or dataset downloads. Run the entire existing suite with optional dependencies installed where practical; list every skip separately.

Run one offline study demonstration on the labeled CIFAR-shaped fixture with at least two search seeds and two independently labeled random arms, using a tiny fixed budget. Verify registry idempotence by repeating `study run`, pause and resume a campaign, export the report, and inspect the plot/table and DB links. A fake Jev transport may be injected in automated tests, but the CLI must never label it live Jev. If official CIFAR data and a real key are available, also run a small paired real random/Jev study under a bounded total trial/API budget; report it as a wiring check, not search-quality evidence. If access is missing, document exact commands and mark that demonstration unverified.

Phase 4 passes when the offline study/recovery/report gates pass and old CLI behavior remains intact. Real-data and live-provider status must be stated separately. Stop before Phase 5.

## Autonomous execution and Git

- Inspect current `AGENTS.md`, `docs/architecture.md`, source, tests, Git status, and local edits first. Update architecture docs only when implemented contracts change. Make routine choices autonomously; keep the study schema small and the existing APIs compatible where possible.
- Commit coherent **passing** units, for example study spec/registry, worker ownership/recovery, timing/checkpoints, reports/tests/docs. Stage only owned files and inspect the staged diff. Never commit data caches, run SQLite files, checkpoints, logs, credentials, local `.env`, or unrelated edits. Do not amend/rebase/reset history or push. If Git author identity is missing, do not invent one; leave an organized diff and report why commits could not be made.
- Finish and commit executable changes before the final recorded demonstrations. A bug fix after a run requires a new session/study under the new source digest; preserve the earlier record. Do not run a large paid or GPU sweep while validating infrastructure.
- Final report: exact tests and skipped gates, demonstrations, study manifest path and report path, crash-safety result, remaining measurement limitations, commit IDs, and Phase 5 handoff. Review your own diff for silent fixture substitution, duplicate campaigns, zombie workers, misleading wall/GPU time, artifact mismatches, and accidental data/secret commits.
