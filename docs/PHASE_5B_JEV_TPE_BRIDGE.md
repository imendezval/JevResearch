# JevResearch — Phase 5B: Jev selection from TPE proposal pools

## Placement and outcome

This is the missing **Option B bridge** after Phase 5 and before Phase 6. `docs/architecture.md` puts classical baselines and Jev plus classical search in Phase 5; Phase 6 introduces a separate autoregressive research agent. The earlier Phase 5 implementation brief intentionally stopped after the baselines. Complete the TPE/Jev combination here, then hand the resulting audited candidate-selection interface to Phase 6. Do not add an LLM in this bridge.

At the repository state reviewed on 2026-09-25 (`main` at `52f35e0`), `GlobalCandidateGenerator` returns one Optuna candidate for `tpe` and `cmaes`, with `SingleCandidateController`. `global-pool` returns up to eight random candidates for Jev or random selection. `OptunaProposer` reconstructs its in-memory Optuna study from the JevResearch SQLite ledger; it has no optimizer sidecar. Reinspect the repository before implementation rather than assuming these paths remain unchanged.

**Deliverable:** a separately named, versioned `tpe-pool` proposal strategy on `cifar-mixed-v1`. Each search step asks Optuna TPE for a complete pool of **2–8 distinct valid configurations**, persists that exact offer, lets either Jev or random select **one**, and trains only that one. Both selection arms use the same proposal procedure, domain, baseline, seed schedule, and pool width. Preserve `tpe` as the existing one-proposal classical baseline and `global-pool` as the random-proposal selector comparison. The selected candidate alone counts against the training-trial budget.

## Why CMA-ES is deferred

The difference is real, not just an inconvenient API. Optuna's TPE accepts conditional/categorical parameters in the mixed domain and supports successive `ask()` calls before an outcome is available. Those calls form a defined **pool policy**; they are not Optuna's internal `n_ei_candidates`, nor a claim that TPE optimizes Jev's choice. For a pool, keep each accepted suggestion `RUNNING` while asking the remaining members and explicitly set/record the `constant_liar` policy. Only actual completed experiments supply objective values. Optuna documents TPE's startup threshold and running-trial treatment in its [TPESampler reference](https://optuna.readthedocs.io/en/stable/reference/samplers/generated/optuna.samplers.TPESampler.html) and `ask()`/`tell()` in the [Study reference](https://optuna.readthedocs.io/en/stable/reference/generated/optuna.study.Study.html).

The existing CMA-ES baseline is confined to `cifar-sgd-numeric-v1` and uses a population of four. Optuna's [CmaEsSampler documentation](https://optuna.readthedocs.io/en/stable/reference/samplers/generated/optuna.samplers.CmaEsSampler.html) excludes categorical distributions; its [sampler implementation](https://optuna.readthedocs.io/en/stable/_modules/optuna/samplers/_cmaes.html) updates the optimizer only when it has at least `population_size` completed solutions from a generation. Asking for four candidates and training only Jev's favorite does not supply those four fitness values. Calling the other three failures, pruning them, or inventing scores does not repair that missing information. Training all four would change the per-decision training budget and the meaning of Jev's selection. **Do not implement a CMA-ES/Jev hybrid in this bridge.** Keep the existing CMA-ES baseline working; revisit a hybrid only with an explicit population-evaluation and budget policy.

## Exact TPE pool lifecycle

For each new search step after the completed baseline:

1. Reconstruct a fresh Optuna study from the authoritative JevResearch ledger using the pinned sampler/options and session seed. Add the baseline once as a completed observation. Replay previous TPE pools **in saved order**, including rejected draws, accepted member order, declined members, the selected member, and its recorded terminal result. Verify that regenerated trial numbers, parameters/config keys, candidate IDs, pool size, and rejection reasons agree with the saved offer. An inconsistency is an error, not an invitation to start a fresh sampler.
2. Draw a full pool of `K` accepted members via `study.ask()` and the existing domain mapper. Retain accepted asks as `RUNNING` until the complete pool has been drawn so the pinned `constant_liar=True` policy applies within a pool. Reject invalid or duplicate draws with `tell(..., state=FAIL)` and no value; use a documented finite draw cap. Exclude the baseline, **all previously offered valid configs** (selected or declined), and earlier members of this pool when checking duplicates. A draw-cap failure yields no partial offer, no Jev call, and no new training attempt; stop with an explicit exhaustion reason. The old single-candidate TPE policy must keep its existing duplicate rule.
3. Assign the same scheduled experiment seed to every candidate in this offer. Persist the exact full specs and canonical candidate order **before** selection, with a stable batch policy/version, trial number and pool slot for each member, domain parameters, and enough per-slot rejection metadata to replay and audit the draw sequence. The durable `offer_id` identifies the batch after saving. No candidate is trained speculatively.
4. Run the existing audited Jev decision path or the existing local random selector on that **saved** offer. Authentication/timeout/invalid response, a crash, or an API-call cap leaves the offer available for the existing retry/resume behavior. A validated Jev decision must still be tied atomically to one pending trial by `Store.select`. Neither a retry nor resume draws a new pool for that step.
5. Once a choice is committed, the unselected Optuna suggestions are closed as `FAIL` **in the reconstructed sampler only**, with no objective value and an explicit JevResearch audit classification `declined_untrained`. They are **not** failed experiments, do not increment `attempted`, and do not enter the best-so-far trajectory. After the selected trial is terminal, tell its measured validation objective on success or `FAIL` without a value on failure/interruption. Use a fixed tell order: close declined pool members in slot order, then close the selected member. No next pool may be generated while the selected experiment is unresolved. Report the distinction between declined suggestions, invalid/duplicate draws, and actual failed training.

This is a replay policy, not an Optuna sidecar transaction. A crash before saving an offer leaves no persistent sampler state, so regenerate the same offer. A saved offer is reused without a fresh `ask`. A crash after validation, after `Store.select`, during training, or after `Store.finish` follows the existing durable recovery path; replay must reconstruct the same sampler state before the next offer. Do not fabricate values for skipped suggestions or treat them as new training trials. If deterministic replay cannot be demonstrated for the pinned dependency and policy, stop and report the mismatch instead of making the hybrid appear resumable.

1. **Pure/cheap tests:** verify legal/illegal arm and CLI pairings; `K=2` and `K=8`; distinct in-domain candidates and fixed seed; actual saved offer identity, order and selected spec; identical first TPE pool for paired Jev/random arms; recorded declined suggestions distinct from failed training; no fabricated sampler objectives; a real adaptive TPE pool after the ten-completed-observation startup threshold; bounded duplicate/invalid exhaustion without a training attempt; and no extra `ask` for a Jev retry.
2. **Recovery tests:** compare uninterrupted and paused/resumed proposals and outcomes for deterministic fake selectors. Inject failure before `save_offer`, after an offer is saved but before/after decision validation, around atomic selection, and around worker completion. Mismatch must fail loudly. Re-run the existing Phase 1–5 suite, especially single-TPE and CMA-ES replay and old-history export tests.
3. **Bounded integration:** run a labeled CIFAR-shaped fixture study with both `tpe-pool` selectors and the single-TPE comparator. Exercise Jev through a deterministic fake transport in automated tests. If official CIFAR data, compute, dependencies and a live Jev key are available, run only a prebounded real-data/live-Jev wiring pair (baseline and at least one selected proposal per arm). Report exact commands, output roots, statuses, calls and blockers. Do not silently launch the full multiseed recipe; use a separate explicit compute budget for that evaluation.
