# JevResearch — Phase 5: classical search baselines on a shared domain

## Starting point and outcome

Start after Phase 4's study and recovery gate passes. The current repository's Phase 1–3 controller chooses one item from a task-defined local-move offer: CIFAR learning rate is halved/doubled, weight decay set to a few values, or SGD/AdamW swapped. That is an excellent Jev-versus-random **selection** comparison, but a TPE sampler allowed to propose any value in a continuous domain would have different access to configurations. Keep that local-move study intact and create a separately versioned **global search domain** for classical baselines.

**Outcome:** reproducible global-random and TPE searches on the same mixed CIFAR-10 domain, plus a separately labeled continuous-only CMA-ES track. Jev and random can also select from the same bounded global candidate pool, so whole search strategies can be compared with clear caveats. All strategies use the existing immutable specs, worker, metric, storage, failure semantics, and Phase 4 study/report infrastructure. Do not add a new training task, SMAC, an LLM, pruning, weight inheritance, or a Jev/TPE hybrid yet.

At implementation time, recheck the installed version of Optuna and its official [TPE](https://optuna.readthedocs.io/en/stable/reference/samplers/generated/optuna.samplers.TPESampler.html), [CMA-ES](https://optuna.readthedocs.io/en/stable/reference/samplers/generated/optuna.samplers.CmaEsSampler.html), and [ask/tell](https://optuna.readthedocs.io/en/stable/tutorial/20_recipes/009_ask_and_tell.html) documentation. Use a pinned optional dependency compatible with the repository's Python support, not a homegrown imitation of these optimizers. Optuna's standard CMA-ES sampler does not support categorical parameters, so it must not silently optimize the mixed SGD/AdamW domain.

## Versioned search domains

Define one task-owned, serialized domain definition and validation/mapping path. Preserve the existing full CIFAR config and fixed protocol fields. Initially:

- **Mixed domain `cifar-mixed-v1`:** categorical optimizer `sgd|adamw`; log-scale learning rate in `[1e-4, 1e-1]`; weight decay as an explicit zero choice or a log-scale positive value in `[1e-6, 1e-2]`; fixed SGD momentum `0.9` and AdamW betas `(0.9, 0.999)`. Make the corresponding Optuna conditional parameters and canonical full-config mapping explicit. Record distribution, bounds, sampler version/options, and domain fingerprint. A zero weight-decay point cannot be represented by a single log distribution.
- **Numeric domain `cifar-sgd-numeric-v1`:** optimizer fixed to SGD and momentum `0.9`; continuous log-scale learning rate `[1e-4, 1e-1]` and positive log-scale weight decay `[1e-6, 1e-2]`. The current baseline `(0.01, 0.0001)` lies in this domain. CMA-ES, TPE, global random, and optionally Jev/global-pool can be compared **within this domain only**. No categorical parameter enters CMA-ES.

`CifarTask.validate` remains the final authority after every mapping. New global proposals are complete valid configs trained from scratch. The old local operators retain their original IDs/protocol and are reported as a different `proposal_domain`; do not pool their outcomes with global-domain arms. Record a proposal's actual origin. `parent_id` means derived from a specific parent; use `None` for independently sampled global configs instead of pretending each came from the incumbent.

## Proposal versus selection boundary

Extend the task/generator contract minimally to support a **proposal strategy** that generates concrete candidates from a versioned domain and recorded history. Keep `Controller.select` for choosing among offered candidates. Existing local random/Jev behavior must continue unchanged.

- `global-random` samples one novel config from the domain; `tpe` proposes one from an Optuna `TPESampler` using completed objective observations. A deterministic one-candidate selector records the selection without calling Jev. Persist the proposal and its sampler metadata as an offer before reserving the trial. Keep a bounded number of invalid/duplicate resamples; if exhausted, stop with a precise reason, without inventing an attempted training trial.
- `global-pool` draws a reproducible bounded set (up to the existing eight-candidate cap) from the same domain and prior used by global random. Existing random and Jev controllers select from this **identical offer rule**, with saved order and full specs. Their trajectories may diverge after selection; that is expected. Do not run Jev on a one-option TPE offer and call it a hybrid.
- CMA-ES proposes one config only in the numeric domain. Set a documented seed/startup/population policy and make its numeric representation unambiguous (e.g. log values mapped back to positive hyperparameters). A two-trial smoke run does not show CMA adaptation. Put a clear `domain` and `proposal_strategy` label in every session/export/study report.

Optuna needs complete past parameter/config and result records, whereas the current `SearchState.history` exposes only trial ID, status, objective, and config key. Add the smallest generic read-only history view or state extension required. Do not let `core` import CIFAR, Optuna, or Jev. The task owns parameter mapping; a narrow optional adapter owns Optuna.

## Durable optimizer state and budgets

The JevResearch SQLite store remains authoritative for sessions, offers, attempted trials, immutable specs, and results. If Optuna uses a study sidecar, persist a mapping from session/offer/trial to Optuna trial number and reconcile it on every resume. Define the behavior around all crash windows: proposal requested before offer saved; offer saved before pending trial; trial finished before `tell`; and `tell` completed before the next proposal. A persisted pending trial must execute without another `ask`. A terminal trial is reported to the sampler **exactly once**. Unmatched Optuna RUNNING proposals are reconciled as abandoned suggestions, not as JevResearch training attempts. If a sidecar is missing or inconsistent, fail visibly; never start a fresh optimizer under an old session ID.

Include the common baseline observation once in each classical sampler's study. For failed/OOM/interrupted training, record Optuna `FAIL` (or the documented equivalent) without fabricating an objective penalty; the JevResearch attempt still counts toward the same trial budget as random/Jev. Persist sampler seed, options, library version, domain version, startup count, proposal/rejection count, and any required state. Graceful pause/resume should yield the same next proposal; after a crash, audit any abandoned suggestion and ensure no duplicate executed config. Pin protocol and source as in earlier phases.

All arms share the same official train/validation split, model, fixed training epochs, baseline and trial-index seed schedule, hardware class, attempted-trial budget, and Phase 4 reporting rules. No early stopping, variable training budget, test-set selection, or parallel workers. Track how many completed observations each adaptive sampler has: Optuna TPE defaults to random startup trials until its threshold, so a budget-two demo is **only wiring**. Distinguish baseline, startup, and adaptive proposals in the export.

## Comparison design and limits

Phase 4's study runner should compare `global-random`, `tpe`, `jev+global-pool`, and `random+global-pool` within `cifar-mixed-v1`; run CMA-ES only with numeric-domain arms. Require a manifest compatibility check for domain/protocol/source, data split, training budget, seed schedule, and hardware. Global random and TPE use the same legal domain; Jev/global-pool evaluates one of several sampled candidates at each step. The latter comparison assesses **whole search policies**, not the isolated ability of Jev to rank identical proposals against TPE. Preserve the earlier local-move Jev-versus-random comparison as the clean selector ablation.

Provide a predeclared recipe for several paired search seeds with a budget large enough for TPE startup and CMA population updates, subject to an explicit compute cap. Show individual best-so-far trajectories, aggregate median/spread across seeds, failures, controller/API time and estimated resource cost. Use validation for search; open the official test set only in a later, explicitly frozen final-evaluation procedure. Do not claim superiority from a fixture, one seed, or two trials. State that this tiny, noisy CIFAR HPO domain is an integration benchmark, not a general AutoML result.

## Verification and acceptance gate

Offline tests with a cheap continuous synthetic objective must verify: domain round-trip and bounds; conditional optimizer mapping; zero weight-decay branch; no duplicate config even with a new trial seed; saved offer/proposal identity; fixed baseline/seed schedule; TPE proposals after its startup period; CMA-ES proposals after at least one population update; invalid/duplicate resample cap; and `FAIL` mapping without objective fabrication. Inject crashes at the four optimizer/ledger boundaries above and compare graceful pause/resume against an uninterrupted run. Re-run all Phase 1–4 tests; no existing random/Jev session should change meaning after migration.

Run a labeled CIFAR-shaped fixture study with small budgets for the mixed-domain global-random, TPE, and random+global-pool arms, plus a separate numeric-domain CMA arm. Exercise Jev+global-pool through an explicitly fake transport in automated tests; do not label it live. Inspect specs, sampler mappings, status counts, and report compatibility. If official CIFAR data/compute are available, run a bounded real global-random/TPE wiring pair (baseline plus at least one proposal each) and, separately, a real numeric CMA proposal. These real short runs validate execution but are too small to establish optimizer quality. If data or dependencies block a real gate, finish the offline implementation, give exact follow-up commands, and label the real gate unverified. A full multiseed comparative study is a separately budgeted evaluation, not something to launch silently during implementation.

Phase 5 passes when both sampler integrations, global-pool comparison path, resume/reconciliation tests, fixture study, and existing regression suite pass. State real-data/live-Jev verification separately. Stop before hybrid Jev+optimizer routing or Phase 6 LLM escalation.
